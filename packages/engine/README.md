# engine

The data model, store, git integration, worktrees, landing, doctor, and updater, implemented as Effect services with no Electron imports. Both the terminal `sm` ([`packages/cli`](../cli)) and the app's host run this engine against a single store.

- [`src/`](src/): one module per service, named after the service (such as [`Store.ts`](src/Store.ts)) and structured according to [`EFFECT.md`](../../EFFECT.md) section 2, with companion pure helpers in lowercase modules beside it. Consumers import each module by name: `@shigomori/engine/Store`.
- [`src/worktrees/`](src/worktrees/), [`src/doctor/`](src/doctor/), [`src/git/`](src/git/), [`src/updater/`](src/updater/), [`src/landing/`](src/landing/): the five largest services, each split by area into sub-makers composed by the service module's `make` ([`EFFECT.md`](../../EFFECT.md), section 2). Each area file documents what it covers, and `documents.ts` holds the errors, documents, and helpers shared across areas. The top-level service module re-exports them so consumers still import `@shigomori/engine/Worktrees`.
- [`src/goJson.ts`](src/goJson.ts): decodes JSON from external programs (such as gh) the way Go's encoding/json does, treating absent or null fields as their zero values.
- [`src/layer.ts`](src/layer.ts): defines the engine's layer graph (`engineLayer`), built once per process by the CLI, the host, and the test sandbox.
- [`src/migrations/`](src/migrations/): the store's schema migration history, which `Store` runs when opening the database.
- [`src/data/`](src/data/): static data shipped with the engine: the launcher catalog and worktree name pools.
- [`test/`](test/): Vitest suite covering the 2.x import and store migrations, what removal, land, Tidy, nuke, or `doctor --fix` deletes or rewrites of the user's data, and recovery from an interrupted move or removal (including a data-folder move). Run the suite with `pnpm run check:engine` from the repo root, or run a single file with `pnpm -C packages/engine exec vitest run test/<File>.test.ts`. [`test/lib/sandbox.ts`](test/lib/sandbox.ts) gives each test an isolated home directory containing a 2.x data dir and an engine instance over its own copy (`box.engine(effect)` runs an effect against it).

Each setting is defined once in contracts: its key and type live in `ShigomoriConfigSchema` ([`packages/contracts/src/schemas/config.ts`](../contracts/src/schemas/config.ts)) for project settings or `DeviceSettingsPatchSchema` for device settings, and its default (when it has one) lives in `PROJECT_CONFIG_DEFAULTS` ([`projectConfigDefaults.ts`](../contracts/src/schemas/projectConfigDefaults.ts), whose type lists every defaulted key) or `DEVICE_SETTINGS_DEFAULTS` beside its schema. [`src/Config.ts`](src/Config.ts) reads and writes settings, and its `deviceKeys` and `projectKeys` arrays control the display order in `sm config list`. Any key omitted from those arrays is listed last. The description shown beside each key in `sm config list` comes from its schema field (`annotateKey({ description })`).

Paths are isolated per flavor ([`src/flavor.ts`](src/flavor.ts)): prod, dev, and each test flavor get their own data dir (`~/.sm`, `~/.smd`, `~/.sm<word>`), pointer file under `~/.config/<configDir>`, command and alias, scheme, and bundle id, so two builds on the same machine never share a file. [`src/Paths.ts`](src/Paths.ts) resolves the active flavor's data dir in order: `SHIGOMORI_DATA_DIR`, then the pointer file, then a pre-2.0 folder still containing state (prod only), then the default path. That table is the single source of truth for these names, read by both app packaging and the CLI build.

The updater ([`src/updateFeed.ts`](src/updateFeed.ts) `pickRelease`) only offers releases newer than the running build in semver order, alpha before beta before rc before the full release: a prerelease build accepts any later prerelease or full release, whereas a full release build accepts only full releases. Among flavors, only prod queries the real release feed, and test flavors use only a stand-in list provided by the lab.

Worktrees live under `wt/`: `<dataDir>/wt/<project>`, `<project>/.shigomori/wt`, or `<dataDirName>/wt/<project>` on the drive ([`src/worktreeLayout.ts`](src/worktreeLayout.ts)). The `wt` folder name is intentionally short to keep paths agents and users read and type all day concise. During migration, the store moves a 2.x data dir's `worktrees/` folders into `wt/` once ([`src/migrations/wtFolder.ts`](src/migrations/wtFolder.ts), [`src/WtFolder.ts`](src/WtFolder.ts)).

The v3 migration reports live progress ([`src/Migration.ts`](src/Migration.ts)): what work this startup owes a 2.x data dir (the JSON import and the move into `wt/`), the state of each step, the move count and which worktree is currently moving, and any worktrees that could not be moved along with git's reason. The store reports import progress while opening and `WtFolder` reports each worktree move, so a process that constructs `Migration` first can display progress while the store is still opening. Move counts are read from the store, so restarting after a crash resumes the count. The app displays this progress on a dedicated page. Only app startup (`migratingEngineLayer`) and `sm doctor --fix` run the migration. All other CLI commands read a 2.x data dir in memory as v2 left it (`Store.fromFiles`) and refuse to modify it. If a running process is using a worktree, the move skips it and reports what to close.

The store is a single SQLite database in the data dir (`store.db`, WAL mode), opened exclusively by the engine with one connection per process. On its first open, it imports the JSON files from a 2.x data dir, including mirror files (`file-sync/git-follow.json` and `mirror-history.json`, each imported by the migration that creates its table). The importer reads files in the format written by the last 2.x release. If a registry, settings, or registered project file cannot be read, or if the project list fails to parse, the import fails and the store refuses to open. Files treated as hints (use logs, marks, worktree titles) are skipped and logged if they fail to parse. Once the import is verified by re-reading the files into memory with zero skips and identical resulting rows, the startup that ran the import deletes the old v2 files ([`src/v2Files.ts`](src/v2Files.ts)). After a skip or any other doubt, all v2 files remain on disk and the doctor reports them.

User-facing and machine-readable output from the engine preserves 2.x `sm` behavior: error wording (including Go-style errno messages and `exit status N` when a child program prints nothing), `--json` document fields, and listing order. Data written by a 2.x data dir or another program is also parsed as leniently as 2.x parsed it. Scripts, hooks, and agents written against 2.x depend on both guarantees, just as they depend on the CLI verbs ([`packages/cli/README.md`](../cli/README.md)).

Because the engine runs under Node in the host and under Bun in the CLI binary, it may only import Node APIs, `effect`, `@effect/*`, `@shigomori/contracts`, and `semver`: no Electron, nothing from the app, and no Bun globals.

## Which platform question to ask

Four platform questions whose answers can differ within the same window:

- **The OS this process runs on**: [`src/platform.ts`](src/platform.ts). Its opening comment explains when an OS difference warrants a separate module per OS versus an inline lookup table (`byFamily`, `byPlatform`).
- **The desktop app or a headless host**: `byHostKind` in [`src/platform.ts`](src/platform.ts), for behavior that differs by machine role.
- **Whose paths these are**: [`packages/ui/src/lib/devicePaths.ts`](../ui/src/lib/devicePaths.ts), which identifies a device's path format from its syntax because one window can display paths from other devices too.
- **Whose keyboard and file manager**: `viewerOs` in [`packages/ui/src/lib/platform.ts`](../ui/src/lib/platform.ts), representing the machine the window runs on, which may differ from the host.

On Windows, project commands run in Git Bash so they follow POSIX sh syntax just as on macOS and Linux, while interactive terminals run PowerShell (PowerShell 7 when installed, falling back to built-in Windows PowerShell). This split is intentional ([`src/Shells.ts`](src/Shells.ts), [`src/shells/windows.ts`](src/shells/windows.ts)).

## Commit points

Every multi-step state change has a single commit point after which it counts as complete. What a crash or interrupt at any other step leaves behind, and how recovery settles it, is documented in each entry below or in its module ([`EFFECT.md`](../../EFFECT.md), section 5). The engine's commit points are listed below by module under [`src/`](src/), and the host's are in [`app/host/README.md`](../../app/host/README.md).

- **The worktree move** ([`worktrees/moving.ts`](src/worktrees/moving.ts)): git's move commits the operation. If a `moving` row is left behind after its process exits, the app's next startup or `doctor --fix` either finishes or undoes it. [`test/Worktrees.interrupt.test.ts`](test/Worktrees.interrupt.test.ts) interrupts the move at every step, and the app's `interrupted-workflows` proof kills the terminal `sm` during it.
- **The re-key and the forget** ([`worktrees/kept.ts`](src/worktrees/kept.ts)): database rows update in a single transaction, followed by updating the dirty capture's git ref.
- **The worktree removal** ([`worktrees/removing.ts`](src/worktrees/removing.ts)): git's remove commits the operation.
- **Land** ([`landing/verbs.ts`](src/landing/verbs.ts)): GitHub's merge commits the operation, and the removal guards run again afterward.
- **Adopt** ([`worktrees/adopting.ts`](src/worktrees/adopting.ts)): the replacement worktree is added before the external checkout is removed, so a crash in between leaves both on the branch rather than neither.
- **The 2.x import** ([`Store.ts`](src/Store.ts)): all migrations commit together. [`test/Store.crash.test.ts`](test/Store.crash.test.ts) kills a database open at forty points during the run.
- **The move into `wt/`** ([`WtFolder.ts`](src/WtFolder.ts)): each worktree move commits as above. Any worktree that cannot be moved stays stuck, recording the reason and offering a Retry.
- **Project removal** ([`Registry.ts`](src/Registry.ts), `unregister`): runs in one transaction, including the primary checkout's marks, shelf, agent sessions, unshelve time, clone records, and icon.
- **Project relocate** ([`worktrees/relocating.ts`](src/worktrees/relocating.ts)): the new path and the data kept for its worktrees commit in one transaction.
- **The updater's swap** ([`updater/swap.ts`](src/updater/swap.ts)), depending on the OS installation format: on macOS, one exchange commits it where the filesystem helper supports one, otherwise two renames ([`updater/bundle.ts`](src/updater/bundle.ts)). On Linux, renaming `current` commits it ([`updater/versions.ts`](src/updater/versions.ts)). On Windows, Velopack's `Update.exe apply` commits it once the updater exits ([`updater/velopack.ts`](src/updater/velopack.ts)).
- **Carry-over** ([`CarryOver.ts`](src/CarryOver.ts)): each entry is renamed as a whole from a staging folder.
- **The data-folder lock** ([`DataDirLock.ts`](src/DataDirLock.ts)): ensures a data-folder move is the only state change in progress, and documents how. The move and its recovery live in [`src/dataDirMove.ts`](src/dataDirMove.ts), invoked by the host with the checks and holds only the host can perform ([`app/host/lib/dataDirMove.ts`](../../app/host/lib/dataDirMove.ts)).
