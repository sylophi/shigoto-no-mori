# engine

The data model and the store, git, worktrees, landing, the cross-device verbs, doctor and the updater, as Effect services with no Electron import. The terminal `sm` (`packages/cli`) and the app's host both run it, on one store.

- `src/`: one module per service, named for it (`Store.ts`), shaped as `EFFECT.md` section 2 says, and its pure helpers beside it in lowercase modules. Consumers import a module by its name: `@shigomori/engine/Store`.
- `src/worktrees/`, `src/doctor/`, `src/git/`, `src/updater/`, `src/landing/`: the five largest services, each split by area into sub-makers that its module's `make` composes (`EFFECT.md`, section 2). An area's file says what it covers; `documents.ts` holds the errors, documents and helpers the areas share, which the service module re-exports, so a consumer still imports `@shigomori/engine/Worktrees`.
- `src/goJson.ts`: JSON from another program (gh) read as Go's encoding/json reads it, a field absent or null at its zero value.
- `src/layer.ts`: the engine's layer graph (`engineLayer`), built once per process by the terminal, the host and the test sandbox.
- `src/migrations/`: the store's schema history, which `Store` runs on open.
- `src/data/`: the data the engine ships with: the launcher catalog and the worktree name pools.
- `test/`: the tests, run by vitest (`pnpm run check:engine` from the root, one file with `pnpm -C packages/engine exec vitest run test/<File>.test.ts`). `test/lib/sandbox.ts` gives each test a home holding a 2.x data dir, and the engine on its own copy (`box.engine(effect)` runs an effect on it); `test/lib/gitRepos.ts` makes throwaway repos for the tests of `Git` alone.

A setting is described once, in the contracts: its key and type in `ShigomoriConfigSchema` (`packages/contracts/src/schemas/config.ts`) for a project or `DeviceSettingsPatchSchema` for the device, and its default, when it has one, in `PROJECT_CONFIG_DEFAULTS` (`projectConfigDefaults.ts`, whose type lists every defaulted key) or `DEVICE_SETTINGS_DEFAULTS` beside its schema. `src/Config.ts` reads and writes them, and its `deviceKeys` and `projectKeys` give the order `sm config list` shows them in; a key missing there lists last. The description beside each key in that listing is its field's (`annotateKey({ description })`), which `packages/contracts/test/settings.test.ts` requires of every key.

Paths are per flavor (`src/flavor.ts`): prod, dev and each test flavor have their own data dir (`~/.sm`, `~/.smd`, `~/.sm<word>`), pointer file under `~/.config/<configDir>`, command and alias, scheme and bundle id, so two builds on one machine never share a file. `src/Paths.ts` finds the flavor's data dir: `SHIGOMORI_DATA_DIR`, then the pointer file, then a pre-2.0 folder still holding state (prod only), then the default. The table is the one place these names are spelled; the app's packaging and the terminal's build read it. The updater (`src/updateFeed.ts` `pickRelease`) offers only a release above the running build in semver's order, alpha before beta before rc before the full release: a prerelease build takes any later prerelease or full release, and a full build full releases alone. Of the flavors, prod alone asks the real feed, and a test flavor only a stand-in list the lab hands it.

Worktrees live under `wt/`: `<dataDir>/wt/<project>`, `<project>/.shigomori/wt`, or the drive's `<dataDirName>/wt/<project>` (`src/worktreeLayout.ts`). Why `wt`: a short folder keeps the paths agents and people read and type all day short. The store's migration moves a 2.x data dir's `worktrees/` folders there once (`src/migrations/wtFolder.ts`, `src/WtFolder.ts`).

The v3 migration reports as it goes (`src/Migration.ts`): what this start owes a 2.x data dir (the import, the move into `wt/`) and each step's state, the move's count and the worktree on the move, and the ones that stayed with git's reason. The store reports its import as it opens and `WtFolder` each move, so a process that builds `Migration` first can show the migration while the store is still opening; the counts are read from the store, so a start after a crash resumes the count. The app's window shows it on a page of its own. Only the app's start (`migratingEngineLayer`) and `sm doctor --fix` migrate: the terminal's other commands read a 2.x data dir as v2 left it, in memory (`Store.fromFiles`), and refuse to change it. The move leaves a worktree a process works in, naming what to close.

The store is one SQLite database in the data dir (`store.db`, WAL), opened by the engine only and by one connection per process. Its first open imports the JSON files a 2.x data dir keeps, the mirrors' among them (`file-sync/git-follow.json` and `mirror-history.json`, each taken by the migration that makes its table). The import reads the files as the last 2.x release writes them. A registry, settings or registered project file it can't read, or a project list that doesn't parse, refuses the import, and the store doesn't open; what it reads as a hint (use logs, marks, a worktree's title) it skips and logs when it doesn't parse. Once the import is verified (the files read again into memory skip nothing and give the same rows) the start that made it deletes them (`src/v2Files.ts`); after a skip or any other doubt they all stay, and the doctor reports them.

What a person or a script reads from the engine reads as the 2.x `sm`'s does: a failure's words (an errno in Go's words, `exit status N` from a program that printed nothing), a `--json` document's fields, a listing's order. What a 2.x data dir or another program wrote is read as leniently as 2.x reads it. Scripts, hooks and agents written against 2.x depend on both, as they do on the verbs (`packages/cli/README.md`).

The engine runs in the host under Node and in the terminal binary under Bun, so it imports Node's APIs, `effect`, `@effect/*`, `@shigomori/contracts` and `semver`, and nothing else: no Electron, nothing from the app, no Bun global. `test/boundary.test.ts` holds that for its sources.

## Commit points

Each change of state in several steps has one step after which it counts as done, and each entry says what a crash or an interrupt at another step leaves and what settles it (`EFFECT.md`, section 5). The engine's, by module under `src/`; the host's are in `app/host/README.md`.

- **The worktree move** (`worktrees/moving.ts`), which every move goes through: `worktrees move`, a rename, the migration's into `wt/` and relocate's. A `moving` row is written before anything moves, by a process that refuses one another live process holds, and git's move commits it. From the record to its delete nothing interrupts it, except a copy across volumes: it goes into a partial sibling renamed in once whole, and is undone if cut. The app's start (before the migration's drain) and `doctor --fix` (`project-interrupted-moves`) take over a record whose process is gone, one process alone. The move landed if git lists its checkout (the `.git` link the record holds) at the destination and no longer at the source; then it is finished, else undone, deleting only what the move made (its partial sibling, or a folder holding its link, the link deleted last so a delete cut short is still the move's to finish). The re-key, which records the move in `wt_moves`, and its mark as carried are one transaction, never repeated; a create refuses a path a record still names; and the record goes last, after the capture's ref followed. `test/Worktrees.interrupt.test.ts` interrupts it at each step, and the app's `interrupted-workflows` proof kills the terminal `sm` there.
- **The re-key and the forget** (`worktrees/kept.ts`): the rows in one transaction, then the dirty capture's ref, idempotently. A re-key never writes over a capture already kept under the new id; a data-folder move's carries only the capture its journal names, and its undo only that one back.
- **The worktree removal** (`worktrees/removing.ts`): git's remove commits it. It, the forget, the empty parents and the branch run uninterrupted; a clock on a cleanup script stops only that script; a create clears what a removal a crash cut short left under the id it mints. git deletes the folder before its entry, so a git killed mid-delete after the `.git` went leaves a managed checkout git lists without it: an unforced removal refuses it as half removed, and a forced one finishes it without the cleanup (the folder wiped, then git's remove of the path). Killed before the `.git`, it leaves a checkout that reads as dirty, or clean if only ignored files went, which a removal takes (`--skip-cleanup` past a teardown that fails on what is left).
- **Land** (`landing/verbs.ts`): GitHub's merge commits it. The removal's guards (`checkRemovable`, the commits the PR doesn't hold) run again after every merge, one GitHub answers at once included, since a commit made while gh merged is in no ref the merged PR holds.
- **Adopt** (`worktrees/adopting.ts`): a locked checkout is refused; then the replacement is added (its own checks first: a folder there, a move naming it), git checking the branch out though the external checkout still has it, and only then the external checkout goes and what it kept is re-keyed, uninterrupted. Just before the removal the original's HEAD must still read as the replacement's, or both checkouts stay, each holding its commits, and the adopt is refused (`adopt-moved`); a commit made in the moments between that read and the removal isn't caught. A removal that fails takes the replacement back only while the original's HEAD still resolves to the commit the replacement checked out; otherwise the replacement stays, holding the commits. A crash between the add and the removal leaves both checkouts on the branch, never neither, and removing the external one finishes it. The add claims its folder as git makes it, so a creator racing for it fails there, before anything is removed.
- **The 2.x import** (`Store.ts`): the migrations commit together, so a crash before them imports again and one after leaves the import. The 2.x files are deleted only once verified; any a crash left are the ones `v2_import` names, which the doctor deletes. `test/Store.crash.test.ts` kills an open at forty points of its run.
- **The move into `wt/`** (`WtFolder.ts`): each worktree's move as above, with no write lock held across it. A row whose worktree git already lists in `wt/` with no record of the move stays stuck rather than carried by its path alone. A store that fails the drain leaves the step stuck with why and a Retry, never a host that can't start; the emptied 2.x roots go at the next start too.
- **Project removal** (`Registry.ts`, `unregister`): one transaction, its primary's marks, shelf, agent sessions, unshelve time, clone records and icon included.
- **Project relocate** (`worktrees/relocating.ts`): the new path and what every worktree that moved with it kept, re-keyed, commit in one transaction. git's repair before it is idempotent, and the dirty captures' refs follow after it, as a move's do.
- **The updater's swap** (`updater/swap.ts`): one exchange commits it, `macfs exchange` where the process has the darwin helper, so the target holds an app at every moment, a crash's included. The old bundle is deleted after it; one a crash leaves is pruned by the next stage. Without the helper, two renames, the aside holding the app between them.
- **Carry-over** (`CarryOver.ts`): each entry is copied whole into a staging folder beside the worktree and renamed in, so an entry is there whole or not at all. A dead create's staging folder is swept by the next create, and the doctor doesn't read it as a stray worktree.
- **The data-folder lock** (`DataDirLock.ts`) makes a data-folder move the one change under way. A change that touches git, its refs or files holds it shared for its run, taken at the engine's entry points: every call that changes code (what a peer needs the `changeCode` grant for), a landing's create, capture and apply as one change wherever it is asked from, every change the host makes through the engine (`asChange`), the auto-pull's fast-forward, and each terminal command that changes a worktree on disk (`changing`, and `changingWithFix` for the doctor's `--fix`). A process holds it shared once however many changes it runs, the changes joining in the order they came, and a change nested in one that holds it joins even while a move waits. A move holds it alone from its first step to its last, waiting 30 s for the changes under way, and a recovery holds it alone too. A hold taken elsewhere is asked for again every 50 ms rather than waited for in SQLite, whose wait under node's driver stops the whole process. A change that finds a move holding it is refused ("the data folder is being moved"), and so is one in a process that found the data dir before a move took it elsewhere (`Paths.current`, read under the hold). A write that only touches the store holds nothing: from before the journal's first write until after it is gone, the store's own triggers refuse every write but the move's (`retireStore`, `asMoveOwner`). Each engine graph built on `engineServices` (all but the doctor's, `doctorLayer`) settles what a move left as it comes up, before anything reads a worktree by its id (`settleLayer`), holding the lock alone (2 s; while a move holds it the store keeps refusing and the next start tries again), and only where the pointer leads now. The move itself is the host's (`app/host/lib/dataDirMove.ts`); its recovery is the engine's (`src/dataDirMove.ts`).
