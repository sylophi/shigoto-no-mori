# v3: the great refactoring

The charter and checklist of the `release/v3` branch. Every PR against `release/v3`
names the item it closes and ticks its box here. The branch merges
`main` every few days. This file goes when `release/v3` merges into `main`.

Written 2026-10-07 from the planning threads listed at the end. Where
a number or a claim below matters to a decision, it was measured or
checked on that day; re-measure before relying on it months later.

Contents: why; decisions; working on the branch; tooling and workflow;
target layout; the engine map; designs; vocabulary; process; steps;
audit findings; measurements; risks; left alone; open; sources.

## Why

v3 changes how the codebase is built, not what the product does. Its
aims, in order: development velocity, robustness, and less to hold in
one head. Line count is not the metric; the metric is whether one
person and their agents can hold the whole thing in their heads.

Two premises. Everyone working here knows the libraries introduced
below, so their learning cost is not an argument. And YAGNI applies to
implementations, never to requirements (`PRODUCT.md`): nothing the
product does gets trimmed to make the build smaller.

What the audits found, in one line each: the code is lean (0.08% copy-
paste, about 4.5k cuttable lines in 177k), the same knowledge lives in
several hand-synced places in two languages, the hard bugs come from
lifetimes, cancellation and errors crossing process and device
boundaries, and the rules for those live in comments (20% of all
lines) rather than in anything the compiler checks. The architecture
scored 8 of 10; its weak spots are five orchestrators near 1,000 lines,
three hand-rolled wire loops, results trusted unvalidated on the
client, and a hub version floor that the comments promise and no code
implements.

## Decisions

Settled with the owner. Each one says why, so a later PR does not
relitigate it.

1. **Effect, all the way, in every TypeScript package.** Services and
   Layers in place of impl slots and global setters, one layer graph
   per subsystem under a scoped runtime, Schema in place of zod, tagged
   errors end to end, Effect RPC in place of the hand-rolled socket,
   and Schedule, Stream, Semaphore and Cache in place of the
   supervisor, heartbeat, watchers, limiter, singleFlight and ttlCache.
   Half-Effect is the worst outcome: two error models, two ways to own
   a lifetime, and a seam between them everywhere. Effect 4 went stable
   on 2026-10-01; its `rpc`, `socket`, `process`, `cli`, `http` and
   `sql` modules are still marked `@stability unstable`, so
   every Effect package is pinned exactly to the newest release at the
   time it is added, and bumped in its own PR. The owner excluded
   `effect` and `@effect/*` from the 7-day release cooldown on
   2026-10-07, since 4.0.x patches ship every few days. The exemption
   is removed once the pinned versions are seven days old (2026-10-14
   for 4.0.2), and later Effect bumps wait for the cooldown unless the
   owner says otherwise. Effect itself is never patched; a gap is wrapped on our side. The
   conventions are `EFFECT.md`, written before any Effect code.
2. **The Go CLI becomes a TypeScript engine package.** Projects,
   worktrees, state, config, git, clone checkout, land and merge,
   doctor, names, launchers, package scripts, the updater: one
   implementation, written once as Effect services, imported directly
   by the host and wired to commands by a thin terminal entrypoint.
   This deletes `cliDelegate.ts`, `cliRunner.ts`, the Go struct twins
   of every zod schema, the mirrored utilities, and the parity proofs.
   It is the single biggest simplification available: two codebases
   become one language. `file-sync/` stays Go because it embeds
   Mutagen.
3. **The terminal `sm` is a Bun-compiled binary.** Measured on a
   trivial script, warm: Go 4.5 ms, Bun compiled and ad hoc signed
   18 ms, a Node single executable 23 ms, plain node 24 ms, Electron as
   node 85 to 95 ms. Bun is the easiest to build and ship and keeps the
   `RunAsNode` fuse off. Two rules keep it safe: the engine uses Node
   APIs only, never Bun globals, and CI runs the CLI proofs against
   the compiled binary, not only the source under vitest. Electron as
   node was rejected: it needs the fuse on, costs 7x startup on every
   shell open, and reworks the updater.
4. **macOS syscalls go in a small Go helper, not a native addon.** Node
   cannot `clonefile` a tree, read or set `st_flags`, list or strip
   xattrs, read APFS private size through `getattrlist`, name the
   filesystem type, or `lstat` to the nanosecond. A helper bundled like
   `file-sync`, lifting the existing `clone_darwin.go` and
   `diskusage_darwin.go` code, exposes those six verbs. It batches: a verifier asks for the flags and
   xattrs of a whole tree in one call that streams results, never one
   spawn per file. Nothing in the engine is native, so Bun and Node
   behave identically.
5. **One SQLite store in place of JSON files with locks.** The
   registry, project configs, marks and state, plus the mirror
   registry, script persistence, mirror history, ports and the device
   id are hand-rolled JSON persistence today, with two writers, a lock
   protocol, atomic renames, file watchers and echo suppression. SQLite
   in WAL mode is the boring mechanism for two processes sharing
   state: writers serialize, readers never block, a relocate is one
   transaction, migrations are code, and change detection is a cheap
   data-version check. The engine codes against Effect's `SqlClient`
   with the node sqlite driver in the host and the bun one in the CLI
   (`@effect/sql-sqlite-node` at 4.0.2, built on `node:sqlite`, so no
   native addon). v3 imports the JSON once.
   `sm --json` covers what hand-reading the files did.
6. **The host runs as its own process, and the local machine is just
   another device.** After step 4 the renderer reaches a host over
   Effect RPC on a socket. The host moves into an Electron utility
   process serving that socket on loopback, so the desktop renderer,
   the web client and remote devices use one path. The Electron IPC
   bridge, the preload transport, the web loopback binding, the
   local-host gating and the two parallel composition roots go.
   Electron main keeps window, menu, dialogs, tray, keychain and
   updater. Host work can no longer stall the window, a host crash is
   a reconnect, and `sm serve` on a box with no screen comes for
   free. The overhead is one process of roughly 60 MB and a startup that
   overlaps with the window loading; a loopback call costs tenths of a
   millisecond, which every remote device already pays. If it ever
   shows in a profile, Effect RPC also runs over a MessagePort handed
   to the renderer with the same contracts.
7. **Streams in place of invalidation.** The host exposes each view as
   a stream (the worktrees of a project, mirrors, script runs) and the
   renderer subscribes. The query-key registry, the remote-viewer cache
   ping, the `movesHostState` flag and the push handlers that write
   into the cache disappear. A database commit becomes a host stream,
   which becomes an RPC stream, which becomes an atom.
8. **Renderer: views and containers.** Every component is one of two
   things. A view takes data and callbacks and only draws. A container
   binds data to a view and has no markup of its own. With atom-react a
   container is a few atom subscriptions. The marketing site renders
   the same views over fixture scenes at build time and hydrates the
   real containers over a fixture-backed host layer for the live
   frames, which is what the lab's fake host does today in an iframe.
   `@effect/atom-react` replaces React Query (64 call sites) and the
   `useSyncExternalStore` stores (12 files), decided at a go/no-go
   after step 4 when the streams exist to feed it. The rule is in
   `app/DESIGN.md`. At the go/no-go (2026-10-09) a spike put three paths on
   atoms beside their React Query twins: a host change reached the view
   about 110 ms sooner (no refetch after the push) with the same renders
   and the same optimistic latency (Measurements). The line is the
   host's views: a stream is an atom, a request stays a query, and a
   family crosses only when the host serves a view of it, so React
   Query stays for requests and the stores that hold view state go.
9. **Real workspace packages.** `contracts`, `engine`, `host`, `ui`,
   `desktop`, `web`, `cli`, `hub`, `marketing`, one pnpm workspace at
   the root, one catalog pinning each dependency once. A package that
   does not depend on `electron` cannot import it, so the boundary
   proof becomes the dependency graph. The single-project layout came
   from the Go split; the marketing PR hit it a second time (two
   Reacts, install ordering, a CSS rewrite plugin), and packages remove
   all three.
10. **Vitest for the proofs, before any Effect code.** It replaces the
    custom runner, the harness half of `checkKit`, and the per-proof
    lefthook selection with `vitest related`. The hub already runs
    vitest. Forks pool, no file parallelism, since proofs spawn real
    git. It changes how every later PR is tested, so it goes first,
    not in the middle.
11. **The wire break is what makes it 3.0.** Effect RPC between devices
    and to the hub replaces the custom framing. The hub gets a real
    version floor (promised in comments today, implemented nowhere),
    the production hub and the web client flip together at 3.0.0, and
    a v2 device gets a clear "update required". A device reaches v3 only
    through the last v2 release, so every pre-v3 migration is deleted.
12. **`hue.go` is dropped.** It only colors project names in CLI
    listings, the app never uses it, and a port needs image decoders.
    The `projects list` JSON keeps its `hue` field, always null.
13. **The CLI's surface is frozen.** Verbs, flags and the JSON output
    stay as they are through the port, so `skills/` and shell habits
    never change. The parity harness against the Go `sm --json` is
    that contract. The Go `sm` stays the shipped binary until the
    switch-over PR.
    With the Go CLI gone, the engine's and the terminal's own tests
    hold the verbs' JSON shapes: the parity cases that survived it.
14. **`main` keeps moving.** No feature slows down for v3. The branch
    merges `main` every few days and pays the cost of re-doing a
    landed feature against refactored code when it happens.
15. **An early go/no-go.** When the first Effect subsystem (step 3) and
    the first engine slice (step 2) land, the owner reads both and
    decides whether the code is something they want to hold in their
    head, before the other hundred-plus PRs.
16. **PR and worktree titles start with `V3: `**, then an ordinary
    title, and branch names start with `v3/`. No step-and-slice
    naming. This checklist tracks which item a PR closes.
17. **The app owns the terminal.** Interactive shells open from a
    worktree, starting there with the environment its scripts get and
    closing when the worktree goes, or free-standing, starting in the
    last folder used (home the first time) and living as long as the
    host. They belong to the host, so a renderer reload or a remote
    device attaches to the same session, and they are built once, on
    the v3 streams, not on today's wire and again after it.

## Working on the branch

One orchestration thread owns this file and hands out items. A thread
handed an item starts from this file and the branch's `CLAUDE.md`,
which says the rest: read this file and `EFFECT.md`, take a worktree
with `sm worktrees create --base release/v3`, name it, keep to the item, tick
the box in the same PR, finalize, and report back.

- PRs target `release/v3`. Titles start with `V3: `, then an ordinary title,
  with the `easy-pr` body style. The worktree's title gets the same
  prefix and its branch starts with `v3/`.
- Lefthook runs the targeted checks on commit; CI runs everything on
  the PR. Nobody runs the repo-wide suite by hand.
- `main` is merged into `release/v3` by the orchestration thread, every few
  days, as a merge commit; `release/v3` is never rebased.
- Dependencies: one catalog, Effect pinned exactly to the newest
  release at the time it is added, bumps in their own PRs. The 7-day
  release cooldown stays for everything except `effect` and
  `@effect/*`, which the owner excluded on 2026-10-07. That exemption
  is removed once the pinned versions are seven days old (2026-10-14
  for 4.0.2), and later Effect bumps wait for the cooldown unless the
  owner says otherwise.
- Two kinds of PR need a human even when green: one that adds or
  widens a diagnostic suppression, and one that changes a product
  default.
- A PR body ends with what was left out and why.

## Tooling and workflow

Kept deliberately small for a one-person project. Each is an item in
step 0 unless it says otherwise.

- **Lint rules as a tested plugin.** `lint/` becomes one rule per file
  with a test per rule, run by vitest, instead of one module. The
  rules for Effect: namespace imports from subpaths, no runtime inside
  a service, no node builtins inside a service, every disabled
  diagnostic says why.
- **knip in CI.** A dead export fails the build; it is the conciseness
  goal made mechanical.
- **`pnpm check`.** One script that is exactly what CI runs:
  typecheck, lint, format check, knip, the proofs, the hub suite.
  Lefthook runs the targeted subset of the same thing.
- **Conventions as review rubrics.** `EFFECT.md` and `app/DESIGN.md`
  are what the finalize review holds changed lines to.
- **The pinned Effect source is the reference.** `node_modules/effect`
  in any checkout is the exact version; agents read it instead of
  guessing an unstable API. No vendored copy, no sync script.
- **Measurements, not budgets** (step 2). The compiled `sm`'s startup
  and size are measured against the Go binary and compared now and
  then, not gated on every commit.
- **Scene comparison on demand** (step 6). Every scene in both themes,
  light and dark, desktop and phone, shot and compared against a base
  (`release/v3` while v3 is built there, then `main`) by a command run
  by hand or in CI, never on commit. The marketing
  thread did this by hand with ImageMagick to prove the view split
  changed nothing.
- **Working rules:** a test that needs a timeout to pass is wrong,
  once its subsystem is on `TestClock`; complexity belongs at the
  adapter boundary and the UI stays dumb; comments describe how a
  thing is used and move with the code; repo-wide checks are CI's job,
  not a local habit. They are in
  `EFFECT.md`, `app/DESIGN.md` and the branch's `CLAUDE.md`.

Considered and left out for now: a vendored Effect source tree, an AI
review action in CI, nightly prereleases and a packaged-app smoke, a
generated error catalog, Renovate. This file stays because it is the
shared context of a hundred agent threads and goes at merge.

## Designs

The shape of the pieces behind the big decisions, so a thread does not
have to rediscover them.

**The store.** One database in the data dir, opened by the engine
only. Tables, roughly: projects, worktrees, marks, project config,
device config, package script order, ports, the device identity, the
usage log, mirrors, mirror history, script runs, the shelf. Launcher
catalog and themes stay data files in the package, not rows. Writers
serialize through SQLite; the app notices the CLI's writes by polling
the data version on a short tick and re-reading what changed, which
replaces the state watcher and its echo suppression. Migrations run on
open; the first imports the JSON files and leaves them in place until
the next release.

**Contracts and annotations.** Every call is an `Rpc` in a per-module
`RpcGroup`. The flags from today's `InvokeDef` become annotations read
by middleware, with the same meanings: `remote` reaches a peer; `gated`
is served to a peer only while the command switch is on; `invitable`
is the mirror invitation's exception, scoped to landing, copy or
project; `tracksProjectUsage` feeds the
usage sorts; `grant` names the consent text that covers the call. A
host-scoped call must classify itself, middleware fails closed on a
missing annotation, and a proof checks every group. The client facade
and the `HostApi` type are generated from the groups. Results are
validated on the client for remote calls and pushes.

**The host process.** The desktop shell spawns the host as a utility
process at launch and connects to it on loopback like any device.
The shell owns the account (Clerk, the keychain) and hands the host
what it needs (the hub token) through an RPC call at start and on
refresh. The device identity is the host's, in its store, and the
shell learns it as the host comes up. The host owns everything else: the engine,
scripts, mirrors, the device link, port forwarding. Quit is the shell
asking the host whether it may, then closing the scope. Terminal bytes
and forwarded ports ride the same byte streams remote worktrees use
today. The web client is the same RPC client over the hub with no
local host, which is what it already is in spirit.

**The web client's tabs.** A browser profile is one enrolled device,
and each of its tabs is a connection of its own, told apart by an id
the tab mints as it dials. A device's kind says how many it may hold.
A web device holds several: the hub relays to all of them, a host's
link holds a set per device with pushes and views per connection, and
presence reads online if any is. A desktop device holds one: a second
connection supersedes the first, and the superseded one stays blocked,
since there it means two app instances on one root. So no tab leads,
none takes over on focus, and nothing can ping-pong between them. The
host's half is in: the link's hello carries the device's kind and the
connection's id (contracts' `link.ts`), and a hello with an id already
held replaces that connection alone, its own redial.

**Streams.** Each view the renderer shows is a streaming RPC on the
host, fed from the store's change notifications and the in-process
state (script runs, mirror sessions). The renderer subscribes through
atoms; nothing invalidates anything. A peer's view is the same stream
over the device link.

**Views and scenes.** Views and primitives live in `ui` with the
stylesheets and the fixture world. A scene composes views over
fixtures; the lab's fake host becomes a fixture-backed host layer the
real containers run over, in-process. The marketing site renders
scenes at build time and hydrates the containers over that layer for
live frames: one React, one shared bundle, islands mounting as frames
near the screen. The `scenes` proof renders every view in Node; the
on-demand scene comparison shoots every scene in every mode against
`main`.

**The terminal binary.** `effect/cli` commands over the engine, built
with `bun build --compile`, ad hoc signed in dev and signed in the
release. Startup and size are measured against the Go binary now and
then. `sm run` spawns the script as a child, forwards signals without
being ended by them, and re-raises the child's signal death so the
shell sees 128+n, except a crash signal, which only exits 128+n. At a
terminal, SIGINT, SIGQUIT, SIGTSTP, SIGHUP and SIGCONT already reach
the child (from the keyboard, the kernel and the shell), so they
aren't sent twice. Node can't tell those from a `kill` aimed at `sm`
alone, which therefore never reaches the script at a terminal. The app
stops runs by process tree, so it isn't affected. SIGTSTP stops `sm`
along with the child: ignoring it, as first planned, froze the terminal
on Ctrl-Z in a pty, since the shell waits for a stop that never comes.
`cliInstall` links the binary into
`~/.local/bin` as it does today.

**The terminal.** A `Terminals` service beside `ScriptRuns`, sharing
its pty layer, theme and replay gate. Each session is a resource in a
scope of its own, its release the kill chain. A session's identity is
`{deviceId, terminalId}`, and its owner is a worktree or the device. A
`terminals` RPC group: `list` as a stream, `open`, `close`, `attach`
(streaming the history, then the output, then the exit), `write` and
`resize`. A window reaches a peer's attach through `hub:watchPeer`, the
streaming twin of `hub:invokePeer` on the hop from the renderer to the
process holding the peer's link, so nothing passes through the cloud
hub. Output is batched as today and carried by the pull-based
stream, so backpressure is the stream's and there is no ack protocol
of our own. Every chunk carries a sequence number, so a reconnect
resumes from the history with no byte duplicated or lost. The size is
a host-side fact: a resize sets it for every attached client. The
history is a ring capped in bytes, with terminal query sequences
stripped so a replay does not answer them again. Sessions survive a
quit as saved history and a fresh shell in the same folder. A terminal
must run a full-screen TUI (an agent CLI) smoothly, so the renderer
uses xterm's GPU renderer and does not render hidden terminals.
Nothing closes a shell behind its user: it closes when they close it,
when its worktree goes, or at a quit, where a shell with a foreground
job counts as busy like a script (the quit asks) and an idle one
closes and comes back as its saved history in the same folder. A remote device's terminals are
the same group over the device link, under the existing run-commands
consent. Custom scripts already run anything, so nothing new is
granted. In the UI, a worktree's terminals sit in a bottom drawer on
its page, with tabs. Free terminals are listed under each device in
the sidebar and reachable from the palette. `TerminalView` and
`TerminalTabsView` are views (`app/DESIGN.md`), and their containers
bind them to `terminals.attach`. The script console keeps its
run-a-slot model and becomes a tab in the same drawer.

**The darwin helper.** A Go program with six verbs: clone a tree
(preserving mode and mtime, as the verifier needs), read and clear
flags, list and strip xattrs, APFS private size, filesystem type, and
`lstat` with nanosecond times (what git's index records, which the
clone checkout's verifier compares, added in step 2). Each
takes a root or a list and streams NDJSON results, validated with
Schema on the engine side. Built and bundled beside `file-sync`.

anymore".

## Process

Same mechanics as v2, which took 99 PRs over 25 days with 8 merges from
`main`, two test prereleases and one rc. Expect two to three times
that.

- `release/v3` is cut from `main`. PRs target `release/v3`, one worktree per PR,
  finalized and reviewed like any other PR.
- `main` is merged into `release/v3` every few days; conflicts are resolved on
  `release/v3`, never by rebasing `release/v3`.
- At each step's end, `main` is merged into `release/v3`, every PR
  that landed on `main` is reviewed against the merge result, a step
  report goes to the owner, and the next step's work waits for the
  owner's check-in.
- Prereleases `v3.0.0-test.*` are cut from the branch (the release
  workflow signs prereleases from any branch; a full release must be
  on `main`). They point at the dev hub until cutover and are
  dogfooded on every device.
- Before the rc: a code-quality review pass, a remote-feature pass and
  a security audit, as v2 did (#272, #281, #285, #305).
- `v3.0.0-rc.1`, then one merge into `main` and the `v3.0.0` tag. The
  production hub and the web client deploy with it.

## Risks

- Effect's unstable modules will have breaking minor releases. Pin
  exact versions; upgrades are their own PRs.
- Clone checkout and the updater are the two places where a port can
  lose data or brick an install. Let the parity harness and the
  differential fuzz test run long there.
- The wire break strands any device not updated through the last v2.
  The version floor makes that explicit instead of silent.
- Simple code gets a little wordier under Effect, and debugging through
  fibers is less direct than plain async stacks. The tracer and the
  conventions are the answer; the go/no-go (decision 15) is the check.

## Left alone

Electron, React and the renderer's UI libraries; the three remote
mechanisms (port forwarding, mirroring, transfer); Mutagen in
`file-sync`; cloudflared; Clerk; the hub on Cloudflare; the villagers.

or jotai, form and hotkey libraries, simple-git or
